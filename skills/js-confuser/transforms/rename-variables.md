# RenameVariables

Source: [`transforms/identifier/renameVariables.ts`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts) — `Order.RenameVariables = 30`.

Upstream docs: [`docs/RenameVariables.md`](../../../encoder/js-confuser/docs/RenameVariables.md)

## 1. Target

Purely cosmetic scope-aware renaming: replace every eligible identifier's name with a
generated one, carrying no information about what it originally named. Not concealment of
data or control flow in its own right, in the sense that it doesn't hide a value or a
branch — but reassigning *every* identifier in the program, including every other
transform's own internal runtime-helper names, is exactly what makes name-based
identification unsafe anywhere else in this pipeline; several other transforms' own
Downstream Effects sections document the specific matchers this invalidates.

## 2. Algorithm

Two passes over the whole Program:

- **Analysis** (`VariableAnalysisVisitor`) crawls every scope once, recording — per
  enclosing function/Program context — which identifier names are *defined* there vs.
  merely *referenced*.
- **Renaming** (`VariableRenamingVisitor`) walks scopes top-down. Entering each scope,
  it decides a new name for every name defined there (`shouldRename`, gated by
  `options.renameVariables`/`options.renameGlobals`'s probability maps, exported
  identifiers, and any name already prefixed `__NO_JS_CONFUSER_RENAME__`), preferring to
  **reuse** an already-generated name from a sibling or now-out-of-scope context where
  safe rather than always minting a fresh one from the shared `NameGen` — this is what
  keeps the total pool of generated names smaller than one-per-declaration would. Then,
  per-identifier, it walks each reference's own scope chain to find which context defined
  it and applies that context's chosen new name.

This pass is also the primary place `__JS_CONFUSER_VAR__(x)` marker calls (see
[Preparation](preparation.md)) get resolved to their final string — since renaming is
what determines each marked variable's ultimate name, this transform swaps the marker
call for the resolved name directly rather than waiting for a later pass.

## 3. Implementation

**Analysis**
([`renameVariables.ts#L40-L104`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L40-L104)):
for every variable-referencing `Identifier`, its "context" is normally
`getParentFunctionOrProgram` — except a `FunctionDeclaration`'s own `id` belongs to the
*enclosing* context (its name is visible one scope out, not inside its own body), and a
`catch` clause's `let` binding gets its *own* dedicated context (block-scoped, not folded
into the enclosing function). Populates three maps keyed by context node: `definedMap`,
`referencedMap`, and `bindingMap` (name → the defining `Identifier` path, used later to
check `isExportedIdentifier`).

**Renaming — per-scope decision**
([`renameVariables.ts#L189-L315`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L189-L315)),
on `Scopable: enter` (top-down, so an outer scope's new names exist before an inner one is
decided):

- **Name reuse** (`possible`,
  [`#L211-L252`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L211-L252)):
  collects every name already generated by an ancestor scope that is *not* referenced
  anywhere within this scope's own subtree (`allReferences`) and not itself one of this
  scope's own defined names — those are safe to hand to a *different* variable here
  without creating a collision, since the two live in genuinely disjoint parts of the
  program.
- **`shouldRename(name)`**
  ([`#L254-L280`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L254-L280)):
  `false` for any `__NO_JS_CONFUSER_RENAME__`-prefixed name; unconditionally `true` for
  any placeholder-prefixed name (`__p_...`, see
  [ObjectExtraction](object-extraction.md)'s Downstream Effects); `false` for an exported
  binding; otherwise gated by `options.renameGlobals` (if global) and
  `options.renameVariables`'s probability map.
- **Picking the actual new name**
  ([`#L282-L311`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L282-L311)):
  pop one name from `possible` if any remain, else mint a fresh one from `nameGen`; either
  way, reject it and retry if it collides with an existing global or a name the generator
  has flagged unsafe to reuse.

**Renaming — per-identifier application**
([`renameVariables.ts#L106-L187`](https://github.com/MichaelXF/js-confuser/blob/31c5a47a79f97e4b4c2d4b2a8552c11a8b548fb0/src/transforms/identifier/renameVariables.ts#L106-L187)):
walks the identifier's own ancestry to find the nearest context that defines its name and
already has a decided rename; a default-parameter `AssignmentPattern` gets special
handling (`paramMap`) since a parameter used as another parameter's default value is only
truly "in scope" for that purpose, not the whole function body. A `__JS_CONFUSER_VAR__(x)`
marker call is swapped for a plain `StringLiteral` of the resolved name directly, rather
than being renamed like an ordinary reference.

## 4. Downstream Effects

None currently documented — `RenameVariables` runs at Order 30, and the only later stages
(`Finalizer` 35, `Pack` 36, `Integrity` 37) don't rewrite its renamed identifiers, they
just operate on whatever names happen to survive to that point.

## 5. Known Quirks

None currently documented.
